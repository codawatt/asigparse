# OCR engine decision: OneOCR (default) with Tesseract fallback

_Status: adopted on 2026-11-11. Detailed numbers: [OCR_BENCHMARK.md](OCR_BENCHMARK.md) (regenerated by
`backend/scripts/benchmark_ocr.py`)._

## Context

The MVP started with Tesseract 5 (`ron+eng`). Operators found it weak on real photos. The alternative tested here is
**OneOCR**, the local OCR engine that ships with Windows 11 Snipping Tool (`oneocr.dll`, `oneocr.onemodel` and
`onnxruntime.dll`). It runs offline on the CPU, with no cloud calls and no per-page cost.

## Result (synthetic benchmark, full pipeline)

Each engine processed 66 documents: 3 sample sets × 11 image conditions × 2 documents. That gives 462
ground-truth field checks per engine.

| | OneOCR | Tesseract |
|---|---|---|
| Fields correct (all conditions) | **95.0%** | 64.9% |
| Critical fields correct (name, plate, VIN, make, model, cc) | **92.6%** | 66.7% |
| Wrong value **not** flagged for review ("silent") | **0** | 1 |
| Documents rejected as unreadable | **0** | 7 |
| Mean time per document | **≈ 0.21 s** | ≈ 1.9 s |
| Clean, phone-photo, perspective, glare, dark, JPEG q18, 35%-scale and 2 px blur images | **100% each** | 24–100% |
| Hardest conditions (20% scale / 3.5 px blur / combined worst case) | 88% / 88% / 69% | 12% / 7% / 19% |

Every OneOCR miss on the hardest conditions was **flagged** (missing value, low confidence or validation error), so
the operator is told to check it. Tesseract produced one confident wrong value (`ANDRE` instead of `ANDREI` on a
blurred card).

### Real documents (added 2026-11-12)

8 real files were tested: CEI scans (front and back), a CEI screenshot, the 1997 CI as a scanned PDF and a cropped
scan, and the 2024+ registration certificate as a 2-page scanned PDF, a screenshot and a phone photo. Each was run
as received and under 8 simulated capture conditions, giving 72 runs per engine. Full anonymised numbers are in
[OCR_BENCHMARK_REAL.md](OCR_BENCHMARK_REAL.md).

| | OneOCR | Tesseract |
|---|---|---|
| Fields correct, original files | **94.3%** | 44.3% (2 of 8 files rejected) |
| Fields correct, all conditions | **77.0%** | 22.0% |
| Critical fields correct, all conditions | **81.9%** | 22.6% |
| Documents rejected as unreadable | **6 / 72** | 37 / 72 |
| Silent wrong values | 8 | 4 |
| Mean time per document | **≈ 0.6 s** | ≈ 7.4 s |

How to read this:
- **The gap is much larger on real documents than on synthetic ones.** Real cards have guilloche backgrounds,
  coloured fonts and small text inside an A4 scan. Tesseract fails to recognise the document at all in half the
  runs, while OneOCR reads every original file.
- **Silent errors:** 7 of OneOCR's 8 are the same l/I confusion in one address abbreviation across conditions, and
  the 8th is a free-text type code. Tesseract has fewer only because it rejects most documents outright.
- **The weak conditions for OneOCR** are blur, heavy JPEG and the phone-photo simulation (about 50%). These were
  applied to the whole page: on A4 scans the card is only about 40% of the width, and the screenshots are already
  550–900 px wide, so the text becomes very small. Rejecting these cases is the intended outcome.
- **The parsers were adapted to these real layouts**, without hard-coding any value:
  - the CEI and its TD1 MRZ;
  - the 2024+ certificate, where the page-2 legend no longer leaks into fields and single-letter codes are read
    by the shape of their value;
  - OneOCR now turns sideways and upside-down pages upright.

  With the same OneOCR output, accuracy on the original files went from 73.9% to 94.3%, and OneOCR's silent
  errors over all conditions from 23 to 8. Because the tuning set and the test set are the same 8 files, these
  numbers are optimistic. A larger, held-out set of consented documents is needed before quoting them.

**What these numbers do and don't show.** All images are synthetic renders of fictitious data (the project must
not use real documents). They contain no guilloche patterns, holograms or wear, so absolute accuracy on real
documents will be lower and is **not measured**. The meaningful result is the *relative* one: on identical inputs,
OneOCR is clearly more robust to blur, low resolution and photo artefacts, and about 9× faster. To confirm this on
real documents, run the same comparison on a consented, access-controlled set with labelled ground truth.

## Decision

- `ASIGPARSE_OCR_ENGINE=auto` (the default) uses **OneOCR when it is installed**, otherwise Tesseract.
  `oneocr` or `tesseract` forces one engine.
- Per-request override: `POST /api/v1/extract?engine=oneocr|tesseract`. The UI has a "Motor OCR" selector.
- OneOCR receives the colour image as decoded. Only images narrower than 900 px are upscaled. Tesseract's
  grayscale + autocontrast preprocessing made no measurable difference for OneOCR (95.2% vs 95.0%), so it is not
  applied.
- OneOCR returns one line per text *segment*. The adapter groups segments into visual rows, de-rotating by the
  detected text angle, so the existing engine-independent parsers work unchanged.

Two parser fixes came out of the benchmark and benefit both engines:
- A partially read certificate holder (only C.1.1 or only C.1.2 for a person) is now flagged as
  `HOLDER_NAME_INCOMPLETE`.
- A misread trilingual label (it contains `/`) is no longer accepted as a name.

## Cost

Both engines are free to run locally. OneOCR adds no licence fee or API cost, but see the constraints below.

## Constraints and risks (read before production)

1. **Unofficial interface.** OneOCR has no public SDK. The adapter (`backend/app/ocr/oneocr.py`) calls the DLL
   through `ctypes`, using the interface published by community reverse engineering
   ([b1tg/win11-oneocr](https://github.com/b1tg/win11-oneocr),
   [AuroraWright/oneocr](https://github.com/AuroraWright/oneocr)). A Snipping Tool update can change or break it.
   That is why the engine is optional and Tesseract remains a working fallback.
2. **Windows only.** OneOCR needs Windows x64 and won't run in a Linux container. A Linux deployment falls back to
   Tesseract or needs another engine behind the same `OcrEngine` interface.
3. **Licensing / redistribution.** The binaries are Microsoft's and are **not committed** to this repository
   (`backend/vendor/` is gitignored). Each machine copies them from its *own* Snipping Tool installation. Before
   any production or commercial use, get a legal review of the applicable Microsoft licence terms. If they don't
   allow this use, switch to a licensed engine (for example the documented Windows AI Text Recognition API on
   supported hardware, or a commercial OCR SDK) behind the same adapter interface.
4. **Provenance check.** `scripts/setup_oneocr.ps1` copies the files only from the installed
   `Microsoft.ScreenSketch` package and refuses DLLs that are not validly Authenticode-signed by Microsoft.
   Verified on this machine: Snipping Tool 11.2608.41.0 (x64), `oneocr.dll` 11.0.15, `onnxruntime.dll` 1.23.2. The
   SHA-256 hashes matched the copies in the handoff archive.
5. **Concurrency.** The native pipeline is not documented as thread-safe, so calls are serialized with a lock
   (about 0.2 s each). That is sufficient for a single-operator demo.

## Setup

```bash
powershell -NoProfile -ExecutionPolicy Bypass -File backend/scripts/setup_oneocr.ps1
```

Then restart the backend. `GET /api/v1/health` lists both engines and whether each is available.
